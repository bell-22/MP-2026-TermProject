### 작업 1. 복합 이벤트 감지 실패 원인 분석

**작업 대상**

- `src/event/event_detector.c`
- `include/system_config.h`
- JTAG UART 출력 로그

**작업 내용**

기존 이벤트 감지 프로그램에서는 진동, 소음, 조도 센서의 단일 이벤트는 정상적으로 감지되었으나, 두 개 이상의 센서에 동시에 자극을 가하더라도 복합 이벤트가 발생하지 않는 문제가 있었다.

기존 `event_detect()` 함수에서는 각 센서가 현재 샘플에서 새롭게 확정한 이벤트 플래그만 비트 OR 연산으로 결합하였다.

따라서 물리적으로 동시에 자극을 가하더라도 센서별 이벤트 확정 시점이 다르면 서로 다른 단일 이벤트로 처리되는 문제가 있었다.

**실제 실험 로그**

```text
[EVENT] 52330 ms | Flags:4 | LIGHT
[EVENT] 52482 ms | Flags:1 | SHOCK

[EVENT] 62360 ms | Flags:4 | LIGHT
[EVENT] 62508 ms | Flags:1 | SHOCK
```

**이벤트 발생 시점 비교**

| LIGHT 발생 | SHOCK 발생 | 시간 차이 | 기존 감지 결과 |
|---|---|---|---|
| 52330ms | 52482ms | 152ms | 각각 단일 이벤트 |
| 62360ms | 62508ms | 148ms | 각각 단일 이벤트 |

**원인 분석**

- 진동과 조도 센서 모두 개별 이벤트 감지에는 성공하였다.
- 센서별 이벤트 확정 시점에 약 148~152ms의 차이가 발생하였다.
- 기존 코드는 같은 샘플에서 확정된 이벤트만 결합하였다.
- 앞서 감지된 센서가 계속 이상 상태에 있더라도 다른 센서의 이벤트 확정 시 복합 이벤트에 포함되지 않았다.

**분석 결과**

복합 이벤트 감지 실패의 주요 원인은 센서별 임계값 자체보다 이벤트 확정 시점만을 기준으로 복합 이벤트를 판정하는 구조에 있다고 판단하였다.

이에 따라 새로운 센서가 감지되는 순간 기존 센서의 이상 상태가 유지되고 있는지 확인하는 방식으로 수정하기로 하였다.

### 작업 2. 복합 이벤트 감지 로직 개선

**작업 대상**

- `src/event/event_detector.c`

**작업 내용**

기존에는 새로운 이벤트가 발생한 센서들의 플래그만 반환하였으나, 이를 수정하여 새로운 이벤트가 확정된 시점에 다른 센서의 이상 상태가 유지되고 있는지 추가로 검사하도록 하였다.

일정 시간 내에 발생한 이벤트를 무조건 결합하는 방식은 실제로 독립된 이벤트까지 복합 이벤트로 잘못 판단할 가능성이 있으므로 적용하지 않았다.

대신 센서별 `latched` 상태와 현재 측정값의 변화량을 함께 확인하도록 구현하였다.

**수정된 동작 방식**

1. 센서값과 초기 평균값의 절댓값 차이를 계산한다.
2. 기존 연속 2회 감지 조건으로 새로운 이벤트를 확정한다.
3. 새로운 이벤트가 없으면 `EVENT_NONE`을 반환한다.
4. 새로운 이벤트가 발생하면 다른 센서의 래치 상태를 확인한다.
5. 해당 센서의 현재 변화량이 복합 이벤트 유지 기준 이상인지 확인한다.
6. 조건을 만족하는 센서들의 이벤트 플래그를 결합한다.

**최초 적용한 복합 이벤트 유지 기준**

| 센서 | 최초 감지 기준 | 최초 적용한 유지 기준 |
|---|---|---|
| SHOCK | 400 | 400 |
| SOUND | 900 | 400 |
| LIGHT | 150 | 75 |

최초 구현에서는 소음과 조도의 유지 기준에 기존 래치 해제 기준을 활용하였다.

이 방식은 최초 이벤트가 확정된 이후 센서값이 일시적으로 낮아지더라도 이상 상태가 유지되는 것으로 판단할 수 있다는 장점이 있었다.

다만 최초 감지 기준보다 낮은 값에서도 복합 이벤트에 포함될 수 있으므로, 실제로 두 센서가 모두 이벤트 감지 임계값을 만족하는 경우만 복합 이벤트로 인정하려는 목적과 차이가 있음을 확인하였다.

### 작업 3. Event History 복합 이벤트 갱신 기능 구현

**작업 대상**

- `include/event_history.h`
- `src/storage/event_history.c`
- `src/main.c`

**작업 내용**

기존 `main.c`에서는 이벤트가 발생할 때마다 `event_history_push()`를 호출하여 새로운 History 항목을 생성하였다.

따라서 최초 SOUND 이벤트가 발생한 후 LIGHT가 추가되어 SOUND+LIGHT로 확장되면 실제로 연결된 하나의 상황임에도 History에는 두 개의 이벤트가 저장되었다.

이를 해결하기 위해 최신 History 항목의 플래그를 갱신하는 함수를 추가하였다.

**추가 함수**

```c
bool event_history_upgrade_latest(
    uint32_t timestamp_ms,
    uint8_t new_flags);
```

**수정된 저장 방식**

1. 최초 단일 이벤트 발생 시 History에 새 항목 저장
2. 기존 이벤트가 복합 이벤트로 확장되는지 확인
3. 기존 이벤트와 최신 History 항목의 발생 시각 비교
4. 새로운 플래그에 기존 플래그가 모두 포함되는지 확인
5. 조건을 만족하면 기존 History 항목의 플래그만 갱신
6. History 저장 개수와 최초 이벤트 발생 시각 유지

**저장 방식 비교**

기존 방식:

```text
[01] 10000 ms | Flags:2 | SOUND
[02] 10200 ms | Flags:6 | SOUND+LIGHT
```

개선 방식:

```text
[01] 10000 ms | Flags:6 | SOUND+LIGHT
```

**개선 내용**

- 복합 이벤트 확장 시 새로운 History 항목 생성 방지
- 기존 이벤트의 최초 발생 시각 유지
- History 최대 10개 저장 구조 유지
- 독립적으로 발생한 새로운 이벤트는 기존 방식대로 새 항목에 저장

### 작업 4. Event Record 복합 이벤트 갱신 기능 구현

**작업 대상**

- `include/event_record.h`
- `src/storage/event_record.c`
- `src/main.c`
- `src/storage/ring_buffer.c` 동작 확인

**작업 내용**

기존 `event_record_trigger()`는 새로운 이벤트가 발생하면 기존 Record의 저장 개수와 이후 샘플 수집 개수를 초기화하고, 가장 최근 이벤트를 기준으로 데이터를 다시 저장하였다.

이로 인해 단일 이벤트가 복합 이벤트로 확장될 때에도 기존 Record가 초기화되어 최초 이벤트 시점부터 수집한 센서 데이터가 보존되지 않는 문제가 발생할 수 있었다.

이를 해결하기 위해 기존 Record의 센서 데이터는 그대로 유지하면서 이벤트 플래그만 갱신하는 함수를 추가하였다.

**추가 함수**

```c
bool event_record_upgrade(
    uint32_t timestamp_ms,
    uint8_t new_flags);
```

**기존 Record 초기화 코드**

```c
record_count = 0U;
post_count = 0U;
```

기존 `event_record_trigger()`에서는 새 이벤트 발생 시 위 값이 초기화되었다.

새로 추가한 `event_record_upgrade()`에서는 해당 값을 변경하지 않고 이벤트 정보의 플래그만 갱신하도록 하였다.

**변경된 동작 방식**

- 최초 이벤트 발생 시 이전 500개 센서 샘플 복사
- 최초 이벤트 이후 500개 샘플 수집 시작
- 복합 이벤트로 확장되면 기존 Record의 플래그만 갱신
- 최초 이벤트 발생 시각 유지
- 이미 수집한 이전·이후 센서 샘플 보존
- 이후 샘플 수집을 처음부터 다시 시작하지 않음

**기존 블랙박스 저장 구조**

| 구분 | 데이터 개수 |
|---|---:|
| 이벤트 이전 센서 샘플 | 500개 |
| 이벤트 이후 센서 샘플 | 500개 |
| 총 저장 샘플 | 1000개 |

**개선 결과**

기존 최신 Record 1개 저장 정책은 유지하면서, 단일 이벤트가 복합 이벤트로 확장되는 경우에만 기존 데이터가 보존되도록 수정하였다.

`ring_buffer.c`의 저장 및 조회 구조는 변경하지 않았다.

이 실험은 복합 이벤트 유지 기준을 SOUND 400, LIGHT 75로 사용하던 버전에서 수행하였다.

**실험 순서**

1. 프로그램 빌드 및 DE1-SoC 보드 실행
2. 초기 5초 동안 센서 평균값 수집
3. 준비 LED 신호 완료 후 감시 시작

5. JTAG UART에서 복합 이벤트 플래그 확인

**실제 복합 이벤트 전환 로그**

```text
[HISTORY] Saved (5/10)

[EVENT] 17660 ms | Flags:5 | SHOCK+LIGHT
[HISTORY] Updated latest flags
[RECORD] Flags updated (capture continues)
```

16233ms에 SHOCK 단일 이벤트가 발생하였으며, 이후 17660ms에 SHOCK+LIGHT 복합 이벤트가 감지되었다.

복합 이벤트로 전환되었을 때 History에 새로운 항목을 생성하지 않고 기존 항목의 플래그를 갱신하는 것을 확인하였다.


최초 SHOCK 이벤트의 발생 시각인 16233ms가 유지되었으며, 이벤트 플래그만 `1 → 5`로 변경되었다.


복합 이벤트로 확장된 이후에도 기존 Record 수집이 계속되어 총 1000개의 센서 샘플 저장이 완료되었다.

### 작업 7. 복합 이벤트 유지 기준 재조정

**작업 대상**

- `src/event/event_detector.c`

**작업 내용**

복합 이벤트 감지 기능의 실제 동작을 검토한 결과, 최초 감지 임계값과 복합 이벤트 유지 기준을 다르게 적용하는 경우 센서 변화량이 최초 감지 기준보다 낮아졌음에도 복합 이벤트에 포함될 수 있음을 확인하였다.

이번 프로젝트에서는 **새로운 이벤트가 확정된 순간 기존 센서 역시 최초 감지 임계값을 만족해야 복합 이벤트로 판정**하도록 기준을 변경하였다.

**변경된 유지 기준**

| 센서 | 최초 감지 기준 | 변경 전 유지 기준 | 변경 후 유지 기준 |
|---|---:|---:|---:|
| SHOCK | 400 | 400 | 400 |
| SOUND | 900 | 400 | 900 |
| LIGHT | 150 | 75 | 150 |

**변경 전 코드**

```c
if (s_sound.latched &&
    sound_diff >= SOUND_RESET_CHANGE_THRESHOLD)
{
    flags |= EVENT_SOUND;
}

if (s_light.latched &&
    light_diff >= LIGHT_RESET_CHANGE_THRESHOLD)
{
    flags |= EVENT_LIGHT;
}
```

**변경 후 코드**

```c
if (s_sound.latched &&
    sound_diff >= SOUND_CHANGE_THRESHOLD)
{
    flags |= EVENT_SOUND;
}

if (s_light.latched &&
    light_diff >= LIGHT_CHANGE_THRESHOLD)
{
    flags |= EVENT_LIGHT;
}
```

**최종 복합 이벤트 판정 코드**

```c
if (flags == EVENT_NONE)
{
    return EVENT_NONE;
}

/* 진동: 변화량 400 이상 */
if (s_shock.latched &&
    vibration_diff >= SHOCK_CHANGE_THRESHOLD)
{
    flags |= EVENT_SHOCK;
}

/* 소음: 변화량 900 이상 */
if (s_sound.latched &&
    sound_diff >= SOUND_CHANGE_THRESHOLD)
{
    flags |= EVENT_SOUND;
}

/* 조도: 변화량 150 이상 */
if (s_light.latched &&
    light_diff >= LIGHT_CHANGE_THRESHOLD)
{
    flags |= EVENT_LIGHT;
}

return flags;
```

**유지한 기존 재감지 해제 조건**

| 센서 | 래치 해제 조건 |
|---|---|
| SHOCK | 변화량 400 미만 |
| SOUND | 변화량 400 미만이 300ms 지속 |
| LIGHT | 변화량 75 미만이 300ms 지속 |

복합 이벤트 포함 기준과 재감지 해제 기준은 서로 다른 목적으로 사용하므로, 기존 재감지 해제 기준은 수정하지 않았다.

**개선 내용**

- 복합 이벤트에 포함되는 모든 센서가 최초 감지 임계값을 만족하도록 변경
- 기존 센서의 래치 상태뿐 아니라 현재 변화량 확인
- 최초 감지 기준보다 낮은 측정값이 복합 이벤트에 포함되는 상황 제한
- 기존 단일 이벤트 감지 및 재감지 제어 기능 유지
- `main.c`, Event History, Event Record 저장 구조 변경 없이 감지 조건만 수정

**현재 상태**

최종 복합 이벤트 유지 기준을 적용한 `event_detector.c` 코드 수정 및 검토를 완료하였다.

다만 해당 임계값 변경 이후의 실제 DE1-SoC 보드 실험 결과는 아직 확보하지 못했으므로 추가 검증이 필요하다.

## 5. 발생한 문제 및 해결

### 문제 1. 센서별 이벤트 확정 시점 차이로 인한 복합 이벤트 감지 실패

**문제**

진동과 조도 센서를 동시에 자극하여도 각각 SHOCK와 LIGHT 단일 이벤트로 출력되는 문제가 발생하였다.

**원인 분석**

기존 이벤트 감지 함수가 같은 샘플에서 확정된 이벤트만 결합하였기 때문에, 각 센서의 확정 시점이 다르면 복합 이벤트를 생성하지 못하였다.

**해결**

- 새로운 이벤트 발생 시 다른 센서의 래치 상태 확인
- 현재 센서 변화량을 이용한 이상 상태 유지 여부 검사
- 조건을 만족하는 센서들의 이벤트 플래그 결합
- 기존 이벤트 확정 및 쿨다운 로직 유지

**결과**

실제 보드 실험에서 `Flags:5`와 `Flags:6`이 발생하여 복합 이벤트 감지 기능의 동작을 확인하였다.

### 문제 2. 복합 이벤트 전환 시 Event History 중복 저장

**문제**

단일 이벤트가 복합 이벤트로 확장될 때 새로운 History 항목이 생성되어 동일한 상황이 여러 이벤트로 기록될 수 있었다.

**원인 분석**

기존 `main.c`에서 이벤트 발생 시마다 `event_history_push()`를 호출하였기 때문이다.

**해결**

- `event_history_upgrade_latest()` 함수 추가
- 기존 이벤트 시각과 플래그 포함 관계 확인
- 복합 이벤트 확장 시 최신 History 항목의 Flags만 변경
- 기존 History 개수와 최초 발생 시각 유지

**결과**

실제 실험에서 SHOCK 이벤트가 SHOCK+LIGHT로 전환되었을 때 History 저장 개수가 증가하지 않고 기존 항목이 갱신되는 것을 확인하였다.

### 문제 3. 복합 이벤트 전환 시 Event Record 초기화

**문제**

새로운 이벤트가 발생할 때마다 Record가 초기화되어, 단일 이벤트 이후 수집한 데이터가 복합 이벤트 전환 과정에서 손실될 수 있었다.

**원인 분석**

기존 `event_record_trigger()`가 매번 `record_count`와 `post_count`를 초기화하고 최신 이벤트 기준으로 데이터를 다시 저장하도록 구현되어 있었다.

**해결**

- `event_record_upgrade()` 함수 추가
- 복합 이벤트 확장 시 이벤트 플래그만 갱신
- 기존 Record의 최초 발생 시각 보존
- 기존 Pre/Post 센서 데이터와 수집 상태 유지

**결과**

실제 보드에서 복합 이벤트 전환 후에도 Record 수집이 계속되었으며, 총 1000개의 샘플 저장 완료 로그를 확인하였다.

### 문제 4. 복합 이벤트 유지 기준과 최초 감지 기준 불일치

**문제**

최초 구현에서는 SOUND의 복합 유지 기준을 400, LIGHT의 복합 유지 기준을 75로 적용하였다.

이에 따라 최초 감지 임계값을 만족하지 않는 센서값도 기존 래치가 유지 중이라면 복합 이벤트에 포함될 수 있었다.

**원인 분석**

복합 이벤트 판정에 최초 감지 임계값이 아닌 기존 재감지 해제 기준을 사용하였기 때문이다.

**해결**

- SOUND 유지 기준을 400에서 900으로 변경
- LIGHT 유지 기준을 75에서 150으로 변경
- SHOCK 유지 기준 400은 그대로 유지
- 기존 래치 해제 조건은 별도로 유지

**결과**

복합 이벤트 포함 기준을 최초 감지 기준과 일치시키도록 코드 수정하였다.

단, 최종 변경된 조건에 대한 실제 보드 검증은 아직 진행되지 않았다.

### 문제 5. 동일 복합 이벤트 반복 저장 및 UART 출력 누락

**문제**

실제 테스트에서 SOUND+LIGHT 이벤트가 반복 발생하면서 별도의 History 항목으로 저장되는 현상을 확인하였다.

또한 JTAG UART 출력에서 일부 문자열이 잘리거나 누락되는 현상이 발생하였다.

**실제 로그**

```text
[EVENT] 21410 ms | Flags:6 | SOUND+LIGHT
[HISTORY] Saved (6/10)

[EVENT] 23000 ms | Flags:6 | SOUND+LIGHT
[HISTORY] Saved (7/10)
```

```text
[CAL] Samples:500 | V:1204 L[AUDIO TEST] Alarm started

[RECOR   11156 ms | V:347 L:136 S:72
```

**원인 분석**

현재 저장 로직은 새로운 센서의 플래그가 추가된 경우에만 기존 이벤트의 복합 확장으로 처리한다.

따라서 기존 이벤트와 동일한 복합 플래그가 새롭게 확정되면 별개의 이벤트로 저장된다.

UART 문자열 누락은 출력량 및 출력 처리 방식과 관련되었을 가능성이 있으나, 정확한 원인은 추가 확인이 필요하다.

**향후 해결 방향**

- 동일한 복합 이벤트의 반복 발생을 독립 이벤트로 저장할지 정책 검토
- 실제 센서 변화와 이벤트 확정 시점 비교
- JTAG UART 출력량 및 처리 시간 점검
- 로그 출력 누락이 센서 샘플링에 미치는 영향 확인

**현재 상태**

현상 확인 완료 / 원인 추가 분석 및 수정 필요
